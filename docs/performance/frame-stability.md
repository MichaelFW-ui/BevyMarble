# 帧率波动排查与优化（2026-10-03）

本轮反馈是游戏刚启动就有卡顿，使用 IDE 的运行按钮启动。排查覆盖构建配置、固定步移动与呈现、文本更新，以及中后期战斗逻辑。下表记录 CPU 压测结果，窗口中的实际帧率仍需在真实对局中观察。

## 定位过程

先核对 IDE 的 Cargo 运行配置，发现使用开发构建：`run --package bevymarble --bin bevymarble`，构建配置为 `dev`。原来的 `Cargo.toml` 没有覆盖开发优化等级，游戏代码、Bevy 和 Avian 都按默认开发配置运行。这是启动初期卡顿的重要嫌疑点，尚未测量它对窗口帧率的独立贡献。

随后检查固定步到渲染的路径，发现领土画面、子弹插值和文字更新各有额外开销或节奏问题。战斗侧沿用离线分析器定位系统耗时，但首次测量暴露了压测负载失真：HQ 被摧毁后，淘汰标记一直保留，每帧补齐的单位又被清理，大球占领等后续系统几乎没有实际工作。那次后期平均约 5.80 ms，大球占领耗时接近零，无法表示持续交战的成本。

先修正分析器，再生成本轮优化前基线：每帧在计时区间外恢复缺失 HQ、重置结束状态，然后补齐主要单位。单步内仍执行正常的命中、淘汰和清理逻辑。修正后的后期平均约 14.95 ms，P95 约 31.96 ms，最大约 80.66 ms；大球占领与子弹命中是主要热点。

## 已完成的修改

### 开发构建优化

`Cargo.toml` 为游戏代码设置开发优化等级 1，为依赖设置等级 3，并保留调试信息。IDE 原有的开发运行命令会自动使用这些设置。首次运行需要重新编译依赖，后续运行使用缓存；依赖更新时仍可能重新编译。配置规则见[Cargo 构建配置官方文档](https://doc.rust-lang.org/cargo/reference/profiles.html)。

### 领土画面呈现最新状态

原来的 `GridFrameBuffer` 保存最多四张完整网格，每次呈现取最旧的一张。模拟追帧时会积压画面，造成领土和单位位置的时间差。刷新阈值为 1/60 秒，每次刷新都将累计时间归零，会丢弃多出来的时间。例如稳定 144 Hz 的呈现周期，每三帧才达到阈值，领土实际刷新约 48 次/秒；接近阈值的帧时间波动也会改变刷新间隔。

现在固定步只标记待呈现的变化，`Update` 直接采集当前网格。一帧内补跑多个固定步只复制一次最新数据。上传资源使用共享缓冲 `Arc<Vec<u8>>`，主世界到渲染世界的提取复用同一份数据；无共享时复用已有 CPU 缓冲。GPU 继续使用持久纹理，变化帧仍上传完整的 1024×1024 单字节纹理。

相关实现位于 `src/territory/render.rs`。脏 tile 计数反映本次采集的脏标记数量，多个固定步的计数相加后最多记 1024；它并不表示局部 GPU 上传量。

### 恢复固定步之间的移动插值

子弹原本带有位置插值组件，Avian 默认插件也已安装插值系统；但 `PostUpdate` 的朝向同步每帧写入整个 `Transform` 的变化标记。下一帧检测到固定步之外的改写时，插值系统会清空位于两个端点之间的位置插值状态，造成固定步之间停顿或跳跃。这个行为已核对本地 0.3.0 版依赖源码，原理可参见[插值库文档](https://github.com/Jondolf/bevy_transform_interpolation)。

现在子弹朝向在 `FixedUpdate` 内、移动之后同步，并只在朝向变化时写入。左侧动态弹珠也添加位置插值组件，文字位置在呈现阶段跟随弹珠。固定模拟频率保持 60 Hz。

### 避免相同文字反复排版

大球数值不断变化，但 `format_value` 得到的显示值可能连续很多帧保持为 `1K`。原实现每次重新赋值，导致 Bevy 将文字标记为需要排版；主系统计时没有包含后续文字排版成本。变化检测行为已核对本地 Bevy 0.17.3 的 `detect_text_needs_rerender` 源码。

现在先比较最终显示字符串，内容变化时才更新 `Text2d`，大球的文字偏移和圆形缩放也只在实际变化时写入。弹珠文字采用相同的字符串判断。

### 护盾保护判定改为机器字批处理

上一版已缓存每格的护盾保护标记，大球占领仍沿每条扫描行逐格判断保护范围并拆分区间。大球半径随体量增长，重复扫描的面积随之增加。

现在为四队分别缓存敌方护盾覆盖的行位图，每个 64 位机器字对应 64 格，1024×1024 网格共约 512 KiB。刷地时，将敌方保护位图与己方领土位图一起用于筛选可占领格子，再批量更新连续字节和队伍位图。预算不足时保留从左到右的逐格消耗顺序，路径顺序、圆形覆盖范围和体量消耗规则保持一致。

相关实现位于 `src/territory/grid.rs` 和 `src/territory/systems.rs`。护盾实体、队伍、位置、半径或网格尺寸变化时重新生成保护位图，单独的耐久变化继续复用缓存。

### 缩小碰撞查询范围并修正计时汇总

碰撞索引记录当前固定步实际存在的最大目标半径和最大大球半径，查询范围据此计算。附近查询使用精确包围框覆盖的桶，减少原来按格数向外扩展带来的多余候选。测试覆盖边界、静止线段和半径大于默认值的护盾。

Profiler 汇总时排除已经包含各子系统的固定步总计时，避免重复相加；面板先结束本帧主世界计时，再读取本帧结果。这个调整提升观察结果的可信度。

## 压测前后对比

命令为 `cargo run --offline --release --bin offline_profiler -- --scenario both --frames 180 --warmup 30`。同一台机器、相同随机种子和参数，预热 30 帧，测量 180 帧。两版均使用修正后的 HQ 恢复策略，计时前最小数量分别为中期 1200 子弹/120 大球、后期 4000 子弹/400 大球。

| 场景 | 阶段 | 平均 CPU 帧耗时 | P95 | 最大耗时 |
| --- | --- | ---: | ---: | ---: |
| 中期 | 优化前 | 11.40 ms | 24.08 ms | 43.48 ms |
| 中期 | 优化后 | 5.63 ms | 10.96 ms | 14.53 ms |
| 后期 | 优化前 | 14.95 ms | 31.96 ms | 80.66 ms |
| 后期 | 优化后 | 8.01 ms | 14.08 ms | 32.56 ms |

中期平均耗时下降约 50.6%，后期下降约 46.4%，后期 P95 下降约 55.9%。逐系统计时中，中期大球占领从 10.246 ms/帧降至 4.725 ms/帧；后期从 8.792 ms/帧降至 3.750 ms/帧，子弹命中从 4.285 ms/帧降至 2.679 ms/帧。完整输出见[优化前样本](samples/2026-10-03-before.txt)和[优化后样本](samples/2026-10-03-after.txt)。

这些是单次采样，机器负载会影响最大值和百分位。CPU 压测包含战斗逻辑、调度、命令应用与网格采集，未包含左侧 Avian 物理、GPU 绘制、窗口合成或完整文字排版，不能直接换算为实际游戏 FPS。以前文档中的实验使用较早的游戏实现与负载维护方式，分别保留在原记录中。

## 验证与后续观察

新增验证覆盖按机器字刷地与逐格参考实现的一致性、有限预算下的消耗顺序、四队领土位图、脏标记、护盾圆形边界、碰撞查询完整性、连续固定步补跑后的最新画面，以及相同显示文字保持变化标记不变。

`cargo test --offline --all-targets` 在优化后的开发配置下通过：23 项测试通过，GPU 测试默认忽略。`cargo build --offline --bin bevymarble` 与 Release 游戏构建均完成，开发构建输出确认启用了优化并保留调试信息。

游戏调度测试设置 60 Hz 固定步和 240 Hz 呈现，验证子弹在固定步之间每帧连续前进。无窗口 Metal GPU 测试读取实际纹理像素，同时确认纹理 ID 在更新后保持不变；该测试已通过。

GPU 验证命令为 `cargo test --offline --release --lib persistent_grid_texture_is_prepared_without_a_window -- --ignored --nocapture`，单独执行后 1 项通过。GPU 测试需要访问本机 Metal 适配器。

优化后仍需用 IDE 启动真实对局观察启动初期和单位增多后的帧时间。高负载样本仍出现约 32.56 ms 的单帧峰值；如果实际对局仍有尖峰，下一步应结合主世界时间、固定步次数和实体数量测量物理与渲染端开销。领土纹理当前仍为整图上传，局部上传可以在明确带宽瓶颈后继续评估。
